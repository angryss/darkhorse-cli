# Project Structure Rules (v2.0)

**Mandatory structure rules for Rust/Tauri desktop projects.**

> **DarkHorse Desktop is a product, not a scaffolder.** These rules define the canonical project structure for Tauri desktop applications that follow DarkHorse principles. They describe the expected layout of a generated or hand-structured desktop project — not the generation process itself.
>
> Future Rust/Tauri project scaffolding will be handled by a dedicated scaffolder CLI (`darkhorse-rust`), which will use these rules as its structural blueprint.

---

## Rule 0: Single Repository Per Project

Every project lives in its **own repository**. The project is **fully self-contained** with no runtime dependencies on any DarkHorse CLI tool.

```
<project-name>/                    ← One repo = one project
├── context/                       ← AI navigation & project context
├── openspec/                      ← Specs, proposals, archive
├── crates/                        ← Rust workspace (Clean Architecture)
├── frontend/                      ← Vite + TypeScript UI
├── deployment/                    ← Packaging, distribution, CI
└── .darkhorse.yaml                ← Scaffolding provenance only (if scaffolded)
```

## Rule 1: Canonical Project Structure

> **This is the ONLY allowed top-level structure for Tauri desktop projects.**

```
<project-name>/
│
├── context/                        ← Project context for AI tools
│   ├── 00-START-HERE.md
│   ├── 10-REPO-MAP.md
│   ├── 30-BOUNDED-CONTEXTS.md
│   └── 50-SEARCH-QUERIES.md
│
├── openspec/                       ← OpenSpec root
│   ├── AGENTS.md                   ← AI agent instructions (READ FIRST)
│   ├── specs/
│   │   ├── architecture/
│   │   ├── domain/
│   │   ├── patterns/
│   │   ├── project/
│   │   └── workflow/
│   ├── changes/
│   └── archive/
│
├── crates/                         ← Rust workspace
│   ├── <prefix>-domain/
│   ├── <prefix>-application/
│   ├── <prefix>-infrastructure/

```

## Rule 2: The `context/` Folder

The `context/` folder is the **AI navigation layer**.

| File | Purpose |
|------|---------|
| `00-START-HERE.md` | Entry point for all agents |
| `10-REPO-MAP.md` | Folder layout and navigation |
| `30-BOUNDED-CONTEXTS.md` | Context inventory and relationships |
| `50-SEARCH-QUERIES.md` | Search recipes for AI tools |

---

## Rule 3: The `openspec/specs/` Folder

Specs define the project's architecture, domain, patterns, and workflow.

In a **scaffolded project** (generated by a future `darkhorse-rust` CLI), these are seeded automatically:

| Folder | Seeded From | Purpose |
|--------|-------------|---------|
| `architecture/` | Scaffolder's `rules/` | Clean Architecture, CQRS patterns |
| `domain/` | Template | Bounded context specs, glossaries |
| `patterns/` | Scaffolder's `guides/` | Backend & frontend patterns |
| `project/` | Template | Roadmap, MVPs, progress tracker |
| `workflow/` | Scaffolder's `workflows/` | Development workflow (agents, commands, skills) |

In a **product repo without a scaffolder** (like darkhorse-desktop today), these are hand-authored to the same structural conventions.

---

## Rule 4: Backend Structure (Rust Workspace)

```
crates/
├── <prefix>-domain/              ← Entities, value objects, domain services (ZERO deps)
├── <prefix>-application/         ← Commands, port traits, orchestration
├── <prefix>-infrastructure/      ← SQLite, filesystem, settings, logging
└── <prefix>-desktop/             ← Tauri host, bridge commands, state
```

Each crate may contain bounded context modules for isolation.

---

## Rule 5: Frontend Structure

```
frontend/
├── index.html
└── src/
    ├── main.ts
    ├── services/
    ├── pages/
    ├── components/
    ├── stores/
    └── styles/
```

---

## Rule 6: Code Goes in the Project Only

ALL code is written to the project repo. There is no `darkhorse-desktop/` or `darkhorse-cli/` folder in a generated or standalone project.

---

## Rule 7: Structure Guardrail

> **These are the ONLY allowed top-level folders:**

| Folder | Required |
|--------|----------|
| `context/` | Always |
| `openspec/` | Always |
| `crates/` | Always |
| `frontend/` | Always |
| `deployment/` | Always |
| `rules/` | Product repos only — hand-authored guidance (not present in scaffolded output) |
| `guides/` | Product repos only — hand-authored guidance (not present in scaffolded output) |
| `workflows/` | Product repos only — hand-authored guidance (not present in scaffolded output) |
| `.vscode/` | Optional |

> **Note**: In a **scaffolded project**, `rules/`, `guides/`, and `workflows/` do NOT exist as top-level folders. Their content lives inside `openspec/specs/` (architecture/, patterns/, workflow/). Product repos that pre-date the scaffolder may have these as top-level folders containing hand-authored guidance.

**No other top-level folders are permitted.**

---

## Self-Containment Guarantee

| Criterion | Required |
|-----------|----------|
| No references to `darkhorse-cli/` paths | Yes |
| All specs readable without external tools | Yes |
| All workflow docs self-contained | Yes |
| `.darkhorse.yaml` is provenance-only | Yes |
| `openspec/AGENTS.md` references only project paths | Yes |
